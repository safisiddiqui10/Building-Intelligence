# Story 5.2: Query Decomposition and HyDE

## Purpose

Make `decomposition` and `hyde` the fifth and sixth real course modes, so all six modes are real at the end of Session 5. Both are small retrieval extensions that sit in front of the existing semantic search. Neither is an agent, a router or a new application.

- **Decomposition** answers a compound comparison question ("compare murder under the BNS and the IPC"). A single similarity search tends to find one side of the comparison. One bounded model step splits the question into one to three subquestions, each is searched on its own, and every accepted subquestion is **required**: if one has no corpus evidence, the mode says so (`partial_answer` or `clarify`) and never writes a complete comparison.
- **HyDE** answers a question phrased in everyday words that the statute does not use ("a phone I bought from a thief"). One bounded model step writes a short *hypothetical* passage; that text is embedded and used **only to find real corpus passages**. It is never an answer source, a citation or evidence.

Both modes are selected explicitly (`rag-decomposition` / `rag-hyde`, or `pattern: "decomposition"` / `"hyde"`). Nothing routes to them. They use the same `QueryRequest` / `QueryResult` contract, the same `RetrievedChunk` evidence, the same grounded-answer path and the same chat streaming as the other modes. They add no provider variable: the model step uses the existing `GENERATION_*` settings (the LiteLLM proxy) and the embedding uses the existing Voyage `voyage-3.5` settings. `semantic`, `hybrid`, `hybrid-reranked` and `structured` keep working exactly as they do today.

Out of scope: agents or open-ended loops, automatic routing, GraphRAG or any graph construction, a general evaluation harness, production security, follow-up conversation memory, new endpoints, new UI screens, re-embedding, re-chunking, any change to the corpus, indexes, Pipe or Filter, and any new or renamed variable.

A retrieved passage is the stored text of the supplied BNS or IPC document. A returned comparison is built only from those passages; it is not a statement about current law.

## Work to do

### 1. One bounded model step (shared helper)

New module `retrieval/model_step.py` with one function that makes **one non-streaming** chat call to the existing generation proxy and returns the reply text.

- Same provider contract as `generation/answer.py`, without streaming: `GENERATION_API_BASE_URL` + `/chat/completions`, `Authorization: Bearer GENERATION_API_KEY`, model `GENERATION_MODEL_NAME`, standard OpenAI body (`temperature` 0, `stream` false), no provider-specific parameters. Timeout is a named constant (about 30 s). **One attempt, no retry.** Accept an injectable transport for tests, as `generate_events` does.
- A `check_generation_config(settings)` runs **before any retrieval or embedding**. An empty `GENERATION_API_BASE_URL`, `GENERATION_API_KEY` or `GENERATION_MODEL_NAME` raises `RetrievalUnavailable` naming the missing variable (for example "GENERATION_API_KEY is not set."), as Story 4.2 does for the re-ranker: HTTP 503, chat error envelope before any stream. There is no fallback to plain semantic search and no invented subquestions or hypothetical text.
- A timeout, connection error, non-2xx (status code only) or a reply with no `choices[0].message.content` string also raises `RetrievalUnavailable` with a short safe message. The key, headers and provider body are never logged or returned. Empty or malformed *text* is not a provider failure: each mode handles it (below).
- Retrieved passages are never put in these prompts. The user question is the only variable input and is passed as delimited data with an instruction not to follow instructions inside it. Prompt text lives in named constants.

### 2. `decomposition`: bounded split, required subquestions

New module `retrieval/decomposition.py` with `decomposition_search(request, settings) -> QueryResult`, reusing `semantic_search`, `build_filter`, `RetrievalUnavailable` and `to_retrieved`-style mapping. No new index, no new MongoDB operation, no write.

**a. Split.** Validate settings (step 1), then make one model call that returns only a JSON object `{"subquestions": ["...", "..."]}`. The reply is parsed strictly: no repair, no code-fence stripping, no second attempt. Accept only when **all** of these hold; otherwise the status is `clarify` with the reason code in the trace:

- `empty`: valid JSON but no subquestions, or an empty reply.
- `malformed`: not a JSON object, no `subquestions` list, or an item that is not a non-empty string.
- `too_many`: more than three (`MAX_SUBQUESTIONS` = 3; never silently truncated). Fewer than one is `empty`.
- `invalid_length`: an item shorter than 10 or longer than 200 characters after trimming (named constants).
- `duplicate`: two items equal after case-folding and collapsing whitespace and punctuation.
- `out_of_scope`: an item that shares no key-word stem with the original question, using the same stem idea as `generation/checks.py` (re-implement the few lines; do not change that module). This stops the model from replacing the user's question with a different one. It is a lexical guard, not a judgement of quality.

A single accepted subquestion is allowed (the model may judge the question not compound); the trace notes `subquestion_count`. A `clarify` for a rejected split has empty `subquestions`, empty `results`, a plain message asking the user to restate the comparison as two clear parts, and **no retrieval and no answer generation**.

**b. Retrieve each accepted subquestion.** Every accepted subquestion is required. For each, in order, run the existing `semantic_search` on a copy of the request with `question` set to the subquestion and `limit` = `min(request.limit, SUBQUESTION_RESULT_LIMIT)` (named constant, 3). The server narrows the act filter when the subquestion names exactly one of `BNS` / `IPC` (or the full act name), using a small fixed rule like Story 5.1's; the narrowing can only intersect with `request.filters`, never widen it, and an empty intersection is `no_evidence` with reason `outside_filters`. A subquestion that names both acts or neither is searched across the allowed acts. `request.required_acts` and `request.chapter` stay ignored and are listed in `ignored_fields`, as in the other modes.

**c. Evidence rule.** Semantic search always returns the nearest passages, so "has evidence" needs a stated rule. A subquestion is `evidenced` only if at least one retrieved passage has `score >= MIN_EVIDENCE_SCORE` (a named constant). Choose the value once, from a short live inspection of the prepared decomposition question and one deliberately unsupported subquestion (for example about a different statute), record the value and the observed scores in the completion record, and do not tune further. State plainly in the code comment and architecture that the threshold is a chosen guard, not a correctness measure. `no_evidence` carries a reason (`no_passages`, `below_score_threshold` or `outside_filters`). Its `results` is **empty**: weak nearest passages are recorded only as ids and scores in the trace and never reach the generator.

**d. Result contract.**

- `subquestions`: one `SubquestionEvidence` per accepted subquestion, in order, with its own passages in `results` (only above-threshold passages for an `evidenced` entry).
- `results`: the **union** of every `evidenced` subquestion's passages, deduplicated by `chunk_id`, ordered round-robin by subquestion (best passage of each subquestion first, then the second of each, and so on). This makes the existing context limit (`MAX_CONTEXT_PASSAGES` 5) keep the best passage of every subquestion; omitted passages are reported by the existing generation trace. A passage found by two subquestions appears once and in both `subquestions` entries. Every real passage in `subquestions` is also in `results`.
- `status`: `ok` (every accepted subquestion evidenced), `partial_answer` (at least one evidenced and at least one `no_evidence`) or `clarify` (the split was rejected, or no subquestion has evidence). A comparison is never presented as complete unless the status is `ok`.
- `message`: one plain sentence naming the status and, for `partial_answer` or `clarify`, which subquestions lacked evidence. `QueryResult.message` never contains an answer. Note that `run_pattern` replaces `message` when a generation runs (existing `with_generation`), so the partial or insufficient reason must **also** be in `trace[0]` (`outcome_reason`) and in each `subquestions[].reason`; do not rely on `message` alone.
- `trace[0]` is a plain dict with no passage text and no secrets: `step`, `mode`, `decomposition` (model name, `accepted`, `rejection_reason`, `subquestion_count`, the original model reply clipped to 300 characters), a `steps` row per accepted subquestion (`subquestion`, `act_filter`, `limit`, `hits`, `best_score`, `kept`, `status`, `reason`, `chunk_ids`, and the ids and scores of passages below the threshold), `min_evidence_score`, `outcome_reason`, `returned` and `ignored_fields`. From `/v1/query` alone a reader can see what the model proposed, what was accepted, what each step found and why the status is what it is.

**e. Answer boundary.** The answer is written only by the existing grounded path over `QueryResult.results`; one request is one decomposition (one model call, up to three searches) and at most one generation operation.

- `ok` and `generate_answer` true: generate with the original question over `results`.
- `partial_answer` and `generate_answer` true: generate over the evidenced passages only, with the **evidenced subquestions** (joined) as the question instead of the original compound question, so the writer cannot be asked for the comparison it lacks evidence for. Open WebUI must see the gap: before the generation events, emit one leading `Text` event of the form "Partial answer — no corpus evidence found for: …" (built from the `no_evidence` subquestions) so the existing `render` shows it. `final_of` must still work (verify by test); if `render` or `generation/` truly needs a change, keep it additive and tiny and say so in the completion record. `main.py` stays unchanged.
- `clarify`: no generation call. `run_pattern` returns the result; chat streams `result.message` through the same path as the other non-answer statuses.
- Context assembly limits, citation and support checks, `MAX_ATTEMPTS`, confidence and DRAFT rendering are unchanged. Confidence describes whether the written claims passed the existing checks; it is not a statement that the comparison is complete. For `partial_answer` the leading notice and the status carry that meaning.

### 3. `hyde`: hypothetical text finds real passages only

New module `retrieval/hyde.py` with `hyde_search(request, settings) -> QueryResult`, reusing `embed_query`, `vector_search`, `load_evidence`, `to_retrieved`, `build_filter` and the RRF constants from `hybrid.py` (`RRF_K`, equal weights). No new index, no write.

**a. Validate first.** Before any model call or embedding, check `MONGODB_URI`, `VOYAGE_API_KEY` and (step 1) the `GENERATION_*` settings. A missing value is HTTP 503 naming it, as in the other modes. Nothing is fabricated: no hypothetical text, no direct-only result presented as a HyDE comparison.

**b. Generate one hypothetical retrieval text.** One model call (step 1) asks for one short plain-text passage, written in the style of a bare-act section, that a document answering the question might contain. Accept it only if it is non-empty after trimming, between `HYDE_MIN_CHARS` and `HYDE_MAX_CHARS` (named constants, about 40 and 1,200) and is plain text (does not start with `{`, `[` or a code fence, and is not a refusal marker). Otherwise the status is `hyde_unavailable` (HTTP 200): empty `results`, empty candidate lists, `hyde_hypothetical_text_debug` null, a plain message, and a trace reason (`empty` or `malformed`). No embedding, no search and no generation call follow, and the message tells the user `rag-semantic` is available for a direct search (a recommendation, never an automatic switch).

**c. Two searches, real passages only.** Embed the original question (existing `embed_query`, `voyage-3.5`, 1,024 dimensions) and the hypothetical text (the same function and model; this choice and its `input_type` are recorded in the trace). Run `vector_search` for each with the same server-built filter and `limit`, and resolve to real passages as `semantic_search` does. Record:

- `hyde_direct_candidates`: the real passages found by the question embedding.
- `hyde_query_candidates`: the real passages found by the hypothetical-text embedding.
- `results`: the deduplicated final real passages, fused by reciprocal rank over the two routes (`Σ 1 / (RRF_K + rank)`, equal weights; ties by better single-route rank, then `chunk_id`), cut to `request.limit`. `score` equals the fused score; the per-route similarity and rank are in the trace, not in new `RetrievedChunk` fields.
- `hyde_hypothetical_text_debug`: the hypothetical text, and **only there**. It must not appear in `results`, `trace`, `generation`, citations, the chat text, logs or any other field. The trace records only its length and the fixed model and prompt names.

Statuses: `ok`, `no_results` (the searches ran and found nothing within the filters), `hyde_unavailable` (above). Failures are never `no_results`: a missing or not-queryable vector index, an embedding failure or a MongoDB error is HTTP 503, as in `semantic`.

`trace[0]` (no passage text): `step`, `mode`, `hypothetical` (`chars`, `accepted`, `rejection_reason`), `embedding` (model, dimensions, `input_type` for each route), `filters_applied`, per-route hit counts and drops, `overlap`, `direct_only`, `hyde_only`, one `candidates` row per fused candidate (routes, per-route rank and similarity, `returned`), `returned` and `ignored_fields`. A reader can see what HyDE added beyond the direct search, including when it added nothing.

**d. Answer boundary.** The hypothetical text is never sent to the grounded-answer writer. When `generate_answer` is true and the status is `ok`, the existing generator receives the **original question** and `result.results` only (real passages), through the existing context, citation, support, confidence and DRAFT path. Other statuses never call the LLM; chat streams the message.
